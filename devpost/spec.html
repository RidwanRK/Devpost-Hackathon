How this works, in plain language

Say this back to someone and your app is understood.

The website Next.js / React

What the student sees and clicks. It never touches the database or the AI. It only asks the backend.

The backend Node + Express

The brain room. Reads and writes the database, and is the only place that talks to the AI. Your API key lives here.

The database MongoDB Atlas

One saved plan for the whole app (no accounts): subjects, topics, availability, sessions, progress.

The AI Gemini free tier

Makes the judgment calls: what first, what to shorten, what to leave out, and why. Answers in structured JSON.

The most important idea: the AI is good at judgment and explanation but can be wrong, so every AI answer goes through a validator that enforces the hard rules. A proposal that breaks a rule is never shown to the student. This is the heart of the “integrating AI” lesson.

The core journey through the system

The POC critical path: Setup → Generate → Miss/Partial → Replan → Review → Accept. PRD ref: The Core Journey, Canonical Demo Scenario

1 · Setup

The student fills the onboarding steps. Generate My Study Plan sends subjects, topics and availability to the backend, which saves them in the database.

2 · Generate

The backend works out minutes available per day until each exam and asks Gemini to place topics, weakest and most urgent first. Gemini answers in JSON; the validator checks it; if valid, the sessions are saved and the dashboard appears.

3 · Work the plan

Completed / Skipped / Partially Completed, minutes and confidence go to the backend as small updates and are saved.

4 · Fall behind

A day passes. The website shows any past, still-planned session as Unconfirmed. It is worked out from the date each time, never stored.

5 · Replan

If Unconfirmed sessions exist, the website shows the confirmation step first. Then the backend computes remaining work per topic and minutes per remaining day, asks Gemini, validates (one automatic repair attempt), and diffs old against new to get the affected sessions. The proposal is saved as “pending”.

6 · Review

The website shows only the affected sessions (original → revised), the Not scheduled list with reasons, the explanation, and the numbers (needed vs. available), which the backend calculated, not the AI.

7 · Accept / Keep original

Accept swaps the pending sessions into the active plan (history is kept). Keep original discards the proposal. The database is updated and the dashboard refreshes.

The AI contract

The part you want to understand. PRD ref: Replan My Schedule › Who decides what

1 · What the backend sends
  • The app date (today)
  • Each topic: id, name, subject, exam date, difficulty, confidence, remaining minutes
  • Each remaining date with its available minutes (the backend does the calendar maths)
  • What happened: missed, partial, unconfirmed-treated-as-missed
  • The current future sessions
2 · What the AI must return 
{
  "sessions":     [{topicId, date, minutes, priority}],
  "notScheduled": [{topicId, minutes, reason}],
  "changes":      [{topicId, kind, reason}],
  "summary":      {neededMinutes, availableMinutes},
  "explanation":  "plain-language paragraph"
}
3 · The seven rules the validator enforces server/src/services/validator.js · unit-tested
  1. The JSON has the expected shape (Zod).
  2. No day's scheduled minutes exceed that day's available minutes.
  3. No session is after its subject's exam date, or before today.
  4. No topic is scheduled for more minutes than its remaining work.
  5. Every topic with remaining work is scheduled (fully or shortened) or listed in notScheduled with a reason.
  6. The AI's echoed neededMinutes / availableMinutes equal the backend's own numbers.
  7. Every topicId refers to a real topic.

If any rule fails: one automatic repair attempt (the broken rules are appended to the prompt). Second failure → the PRD's “We couldn't generate your revised plan…” message with Retry. The bad proposal is never shown or saved.

Builds the prompt and JSON schema, calls Gemini once, parses the result. One function, two modes (generate and replan), so the first plan and every replan share one code path. It never decides if a proposal is acceptable.

Validator services/validator.js

Pure, unit-tested checks of the seven rules above. Returns the list of broken rules (empty = valid).

Replan workflow services/replan.js

Cheap on-track check (nothing missed, partial, unconfirmed or edited → no AI call) → gather inputs → AI planner → validate with one repair attempt → diff old vs. new into affected sessions → save pending → later accept or discard. An identical proposal also returns “on track”.

Data model

One collection, one document, minutes as the unit, dates as YYYY-MM-DD.

StudyPlan {
  key: "demo"                                   // one document only
  demoDayOffset: Number                         // demo clock
  availability: { mon … sun }                   // minutes per weekday
  subjects: [{ id, name, examDate,
               topics: [{ id, name, estimatedMinutes,
                          difficulty 1-5, confidence 1-5 }] }]
  sessions: [{ id, topicId, date, plannedMinutes,
               priority, status: planned|completed|skipped|partial,
               actualMinutes?, confidenceAfter? }]
  notScheduled: [{ topicId, minutes, reason }]
  explanation: String
  editedSinceLastPlan: Boolean
  pendingReplan: null | { sessions, notScheduled, affected, summary, explanation }
}
Unconfirmed is not stored

It's worked out each time: date before the app date and status still “planned”.

Credited work

Completed credits actual (or planned) minutes; partial credits actual minutes; skipped and Unconfirmed credit nothing. Remaining = estimate − credited.

Accept

Replaces all still-planned sessions dated today or later with the proposal; keeps history. Past Unconfirmed sessions stay Unconfirmed.

Start Over

Deletes the document (and resets the demo clock).

Actual-time rules

actualMinutes must be between 0 and plannedMinutes. Completed with no time entered credits the planned minutes. Partial requires actualMinutes and credits exactly that. Enforced by the backend.

Important failure modes

Gemini slow, rate-limited or down

Original plan unchanged. “We couldn't generate your revised plan. Your current schedule is safe—please try again.” + Retry. Request timeout. No progress lost.

AI returns invalid or rule-breaking JSON

One automatic repair attempt; then the same failure message. The bad proposal is never shown or saved.

Backend or Atlas unreachable

“Can't reach the server. Check that it is running.” Each change is one save to one document, so nothing is half-saved.

Replan when nothing changed

“You're on track!” with no AI call; also if the AI's proposal equals the current plan.

Simplifications and decisions

What was simplified
  • One embedded document, no accounts.
  • Next.js only as a React frontend; Express does all backend work.
  • One AI code path for generate and replan (no separate hand-written scheduler): one AI call per plan or replan, with at most one additional repair attempt if validation fails.
  • No streaming, queues or background jobs.
  • The backend computes the numbers and the affected-session diff; the AI doesn't.
  • Plain CSS, plain JavaScript, no UI kit.
  • Tests use a canned AI response (test fixture only). The running app and the demo always call the real AI.
Needs your explicit agreement (my additions)
  1. Demo clock. A labeled control that advances the app date by a day. Without it, “miss Day 1, replan on Day 2” can't be shown in one sitting. Not in the PRD. Alternative: a seed script that inserts the scenario already at Day 2, labeled as sample data.
  2. JavaScript, not TypeScript, and one embedded document.
  3. Auto repair attempt: one retry with the broken rules listed before showing the failure message.
Your learning focus: “everything about AI integration”

That is too big for one step, so the agreed small investigation is a smoke script in the first build slice. It sends the canonical scenario to Gemini with the JSON schema, prints the raw answer, runs it through the validator, and also feeds a deliberately broken answer to the validator. Evidence it worked: a valid answer passes, a broken one is rejected naming the specific rule, and you can say in your own words why the AI's answer is never trusted directly. It also verifies the “verify” items.

Still open (carried to the build)
  • The “verify” items: Next.js version, Gemini model name (default guess gemini-2.5-flash, one env variable), SDK call shape, free-tier limits and terms, Atlas M0 availability.
  • License choice (MIT default) and any optional hosting: decided in 6-ship.
  • Session time: a completed session may omit actual time and then credits its planned minutes; a partially completed session must include actual minutes between 0 and its planned duration. Enforced by the backend.
